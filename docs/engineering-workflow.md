## 2. 人员、运行时与职责分工

| 责任主体 | 负责内容 |
| --- | --- |
| Codex | Host、Agent、整体接入、主链路集成和回归；也可直接开发 Extension 本体 |
| Qoder | 在具体任务明确分配时开发分析资产、连接器和业务插件，交付规格、测试、接入说明及证据 |
| 独立复核 Agent | 在全新、聚焦且不继承作者会话历史的上下文检查固定候选，独立于该候选的全部作者 |
| 用户 | 产品方向、重要范围与边界决定，以及适用的产品验收 |

Codex 与 Qoder 遵守同一工程规范。每项变更明确修改范围、文件归属、接入责任和验收。一般并行实现使用各自分支和独立工作目录；同目录协作明确不重叠的文件归属，不并发切换分支，不覆盖 WIP。公共契约由相关责任方协商并记录；独立复核源文件只读，验证产物写入隔离位置。

每项 Extension 变更明确本体实施者。Codex 直接开发时，连续负责本体、接入、验证和交付。设备分工、长期分支、试用目录和运行入口按后续任务确定，不继承 OptraCall 的具体机器安排。

### Qoder → Codex 移交交付模式

这是既有分工的一条可选交付路径，适用于 Qoder 开发并将候选交由 Codex 接管至合并的变更。采用本模式时，在当前变更规格记录安排与范围。

1. **Qoder 开发。** 在 `qoder/<slug>` 分支的独立工作树实施 Extension。Host／Agent 接缝由 Codex 实施；仅在用户对本变更直接指定 Qoder 实施接缝时，Qoder 才可承担该部分，并按 IN06 在规格记录例外的范围、理由及后续维护回归 Codex 的安排。先例、一般“开工”指令或自行填写 IN06 记录均不构成该指定。完成规格、适用 SDD/TDD、届时定义的统一检查命令、隔离环境端到端及浏览器点验，保留失败与未验证项。变更目录提供候选文件清单与哈希、结果和证据索引，以及包含接缝互查导引、非作者复核任务书和移交声明的移交包。
2. **分支移交。** 在有效 Git 授权内将全部候选与移交包固定为单一交接提交，推送 origin；原工作树切为游离状态释放该分支，并停止写入。交接提交、基线、原工作树及候选身份须可核对。移交即分支所有权转移，此后唯一写入者为 Codex，Qoder 保持只读。
3. **Codex 接管至合并。** fetch 后在自己的独立工作树检出该分支，先核对提交与清单哈希，再完成接缝互查、直接修复、提交和受影响检查；修复持续由 Codex 承担。固定修正后的完整候选，以全新、干净上下文的非作者子 Agent 完成第4节独立复核，处理发现并请其重验。按当前用户授权执行第5节 Git/CI 交付：需要授权时由 Codex 申请，集成最新 main 并重验受影响部分，集中单 PR、实际 head CI，获用户合并确认后 squash 合并并安全快进本地 main；更新规格/结果并完成适用 OpenSpec 归档。

移交前后同一分支同一时刻仅有一个写入者。独立复核者须未参与候选任何部分的创作，且不继承作者会话历史；接口互查与作者测试仍按第4节单独报告。本模式不改变 IN01–IN07、职责边界及复用检查、独立复核的强制要求，也不扩大模型、数据、设备、安装或运行采用授权。

未经上述直接指定实施接缝时，在结果记录保留流程偏差、实际范围及用户后续决定；事后知情接受、保留实现或 Codex 互查兜底不追溯改写为原流程合规。

### 四点产品原则

本项目统一遵循：**Host 管环境、Agent 自主执行、优先复用获准第三方 SDK 已有能力、减少人的操作**。以下职责及复用规则是详细来源；每次 spec／UI 设计、开发和验收均须实际检查，不能只在方案中重复原则口号。

### 产品 Agent 与工程 Agent

本项目遵循“Host 管环境，Agent 自主执行”的架构原则。Host 负责提供任务目标、业务上下文、资源与工具访问、权限边界、预算与取消控制，以及交互、状态展示、日志、成果持久化和决策学习环境；产品运行时的 Agent 在授权范围内自主理解任务、选择方法与工具、安排分析步骤、检查结果并修正错误。Host 不通过硬编码分析流程、固定步骤、方法配额或无必要的确认门槛干涉 Agent 的内部运行，不替 Agent 作业务判断、补跑计算或编排其推理过程。这里的自主性不改变 Codex、Qoder 的 SDD/TDD 与独立复核责任。

Host 对越权、资源超限和破坏性操作实施必要约束，保护原始材料与历史成果；这些环境治理职责与 Agent 自主执行并存。校验失败应尽可能将具体问题反馈给 Agent 在授权范围内自主修正，不在 Host 中另造分析流程；业务适配器按已确认契约进行结构／格式校验、保存和回执，仍遵循下述 IN01–IN07。

后续方案如采用 Pi，统一使用官方 **pi-coding-agent SDK** 承担 Agent Runtime，由 Codex 维护产品级接入与运行管理入口；当前尚未选定或安装 SDK。Extension 通过统一入口提供工具、skill、上下文及专业能力，不自建 SDK 接入层、会话运行管理或平行 Runtime。具体组件选型与精确版本由后续已批准方案及用户授权确定。

会话循环、工具调用、上下文管理、压缩、恢复与重试等能力优先复用既有 SDK／Runtime。仅在存在已验证的能力缺口时增加最小适配，并在变更规格中记录实际版本、验证证据、缺口及最小适配理由，不重复建设平行机制；恢复与重试仍须遵守原有取消、UNKNOWN 和副作用保全边界，不盲目重放请求。

统一底座允许按任务隔离会话与上下文。所需会话的创建、续接、停止及事件处理均经过统一入口；具体接口与并发方式随实际任务确定。采用 Pi 时，宿主不直接组合 pi-agent-core + pi-ai 自建运行底座；SDK 内部的传递依赖不受此限制。实施时核对并锁定兼容版本，不能将“已声明同一依赖”当成实际共用 Runtime 的证明。

人的操作围绕表达目标、指定资料或偏好、纠正／排除，以及确需由人作出的授权和不可替代的业务取舍。正常使用优先让 Agent 在已有授权内完成查找、读取、方法选择和纠错；用户无需为享受能力先维护日记、搬运资料、逐条审批普通读取、填写机器身份或确认引用。可选管理与人工指定资料作为补充，默认沿已有当前工作和合理值，技术细节按需展开。减少点击不能以 Host 代作专业判断、暗中放宽权限、擅自丢弃用户明确选材或越过必要确认实现。

所有新增设计均须检查四点原则：是否属于环境与治理职责、是否侵入 Agent 自主执行、是否重复 Pi／既有 Runtime 能力、是否把可由 Agent／SDK 完成的工作推给用户。Pi 已支持的工具组合／嵌套、分支、上下文与重试方式优先沿用；权限或持久副作用确需收窄时记录实际缺口／风险依据，不能只为日志更整齐或新证明协议限制 Agent 的正常方法。职责越界、重复建设或非必要人工作业应先删减、合并或调整；确需例外时按第4节记录并批准，不将必要授权和保护误省。

### 官方组件来源与版本约束

适用于后续获准引入的第三方 SDK，包括 Pi、Semantica 等。首装采用与精确版本须在方案及授权中确定；默认使用未经修改的官方发行包，兼容适配由本项目承担，版本升级须用户授权。下列专属规则均按实际采用条件执行。

### 官方 Pi SDK 来源与版本约束

1. **官方包保持原实现。** 采用 Pi 时，统一使用官方发布的 pi-coding-agent SDK，经项目统一入口使用。不得直接改写官方包的源码或安装目录中的构建产物，不通过补丁、私有 fork、包别名／本地替代、模块加载替换等方式改变官方实现；也不得绕过官方公开契约改写 SDK 内部对象、方法或原型。使用官方公开配置、事件钩子、工具注册和扩展机制，或在 OptraSentiScope 自有对象上包装调用，属于产品适配；不能仅因代码位于 Host／Extension 就认定原位改写 SDK 对象合规。用户指定版本后的标准包管理安装属于官方版本采用，不是手工改包。只读使用内部接口按下述例外管理，不等于获准修改它。
2. **版本由用户指定。** 保持当前已确认并锁定的官方版本。只有用户明确指定升级目标后，才能在相应授权范围更新到该官方发布的精确版本；记录用户指令与目标，不把 `latest`、浮动范围、安全提醒或自动依赖机器人当成版本决定。未经指定，不自动升级、替换或降级；可以主动提示官方新版本、变化和潜在影响。SDK 及其官方 Pi 依赖的替代／覆盖同样受此约束，不能借 `overrides`、别名或安装脚本绕过。第三方依赖覆盖若影响 SDK，另记录实际解析版本、理由和兼容证据。
3. **适配归 OptraSentiScope。** 先核对目标版本的官方发布说明、变更及公开接口，优先在 Host、Extension 和必要薄适配层解决差异，逐项遵循四点产品原则，不重造 Runtime 或分析循环。确实无法通过官方公开接口、配置或扩展机制解决时，说明缺口、影响和可选产品安排，交用户决定；不能自行修改 SDK。内部接口确有必要时，按 IN06 记录路径／符号、公开能力缺口与证据、owner、精确版本约束、升级失效风险、替代／移除条件及独立复核结论；版本改变后重新核对适用性，不能自动继承旧例外。
4. **来源与实际采用分别证明。** 同时核对依赖声明、锁文件的官方 registry 来源／完整性、实际解析目录／版本及有关官方 Pi 依赖；必要时将安装包与该版本官方发布归档逐文件比对。包名、锁文件或统一入口检查通过，均不能单独证明安装包未改、运行时无不受支持的改写或正在运行的服务已采用新版本。版本提醒／模型目录刷新也不构成 SDK 升级授权。

### Semantica 官方组件来源与版本约束

后续方案如采用 Semantica，其业务语义支撑职责与 Agent Runtime 分开，官方组件治理要求与 Pi 一致。本节为 Semantica 的长期规则来源，升级执行第3节的[验证与回退流程](#semantica-升级验证与回退)。

1. **使用官方原包。** 采用未经修改的 Semantica 官方发布包；不改源码或 `site-packages` 安装产物，不通过补丁、私有 fork、同名替包、模块替换或绕过公开契约的运行时改写改变其实现。通过官方公开 API、配置和扩展机制操作自有实例及业务图数据属于正常使用，不把合法图数据更新误当成改包；业务本体、图数据、来源映射和适配代码维护在 OptraSentiScope 自身资产与代码中。
2. **版本由用户指定。** 保持已批准并锁定的版本。只有用户明确指定精确升级目标后，才按授权更新官方依赖与对应平台锁文件；不因 `latest`、安全提醒、依赖机器人、重装或依赖重解算自动升级、替换或降级 Semantica。可主动说明官方版本变化和影响，不能代替用户决定。关联 Python／传递依赖的变化须记录理由、实际锁定版本和兼容证据，不能借其绕过组件版本决定。
3. **适配在 OptraSentiScope 完成。** 先核官方发布说明与变更，优先使用公开接口，在 Host、Extension 或必要薄适配层处理差异，遵守四点产品原则。Semantica 不成为第二套 Agent Runtime，也不接管业务方法、原始资料或其他业务资产的来源与发布权威。确有必要只读依赖内部接口时，按 IN06 记录公开能力缺口、owner、路径／符号、精确版本、升级风险与替代条件，逐版重核；无法解决时说明影响交用户决策，不自行修改官方实现。
4. **核对来源及实际安装。** 检查官方发行来源、精确版本、平台锁文件与 wheel 完整性、实际私有解释器／导入目录／分发版本及依赖闭包，必要时逐文件对照官方归档。相同版本号或安装命令成功不能单独证明原包完整，也不能证明运行服务已采用；工程核验不放入每次产品启动或日常查询中增加用户操作。

### 统一会话接入规范

继承 OptraCall IN01–IN07 的职责、生命周期和验证约束。当前没有会话实现、Interface 版本或业务 profile；后续实施时在规格和接入说明中定义实际入口、类型、版本与兼容范围，不把 OptraCall 的 Interface v1/v2/v3、源码路径或业务策略写成现成能力。

| 标识 | 必须遵守的接入规则 |
| --- | --- |
| IN01 开发前必读 | 新增/修改Agent交互、SDK接入、会话启停/恢复、模型配置或插件接入前，读取本节及届时已建立的接入说明；本变更规格记录规则/Interface版本、owner/profile、修改范围、业务差异和验收。旧任务授权不替代当前范围。 |
| IN02 Host注册与注入 | Host静态注册域/profile并注入能力受限的port及绑定owner的Ref；业务前端保留自身入口。域构造、跨owner管理留在Host，插件只取得自己的会话资格，不接收可自行注册域或清理全局会话的管理对象。 |
| IN03 共用生命周期 | 启动、占用、取消、关闭及订阅经公共入口；业务层不直接创建SDK会话或Runtime实例，也不另写opening/operation/代际Map、配置监听及全局清理。公共实现创建多个隔离实例属于正常复用，业务Store和业务集合仍各自维护；同一资源只有一处权威生命周期状态。 |
| IN04 保留业务差异 | profile仅声明真实差异：准入、模型选择、工作区/工具和续接参数。业务上下文、业务资产校验、保存/回执、事件投影及有限修正留在业务适配器。多turn明确结束与取消条件；公共层按技术能力工作，不按业务名加入流程分支。 |
| IN05 Host资源权限 | 凭据解析、原生资源创建和跨owner清理由核准Host路径负责。插件只使用非敏感引用及获准能力，不通过消息中的任意workspace/sessionFile、密钥或Provider绕过配置；事件与日志继续脱敏，会话port不扩大数据或经营动作授权。 |
| IN06 契约共同维护 | 新能力先补契约、消费者适配与验收。Codex 负责 Host／Agent 集成与主链路，Extension 实施者交付接入说明及证据。涉及另一方职责的契约变更由双方协商并记录。不兼容变化或范围扩大先补适用决定。底层导入例外的新增或变更须说明理由并独立复核。 |
| IN07 交付验证 | 交付覆盖正常路径、取消、配置变化、迟到结果、保存/恢复与兼容范围；公共改动复测现有消费者及第三合成接入。导入约束加入届时定义的统一检查命令及CI，合规样例通过、受控绕过样例失败、恢复合规后通过；不能靠跳过检查、删除断言或扩大白名单制造通过。 |

未知结果保留 UNKNOWN／中断，不自动重放或换模型。取消先撤销后续派发，再等待匹配操作及资源安全停止；清理失败隔离受影响资源并保留事实。模型配置、会话、上下文与占用按实际 owner 隔离，不建立平行 Runtime 或全局业务运行队列。逻辑隔离不等于进程或安全隔离。

## 3. 连续 SDD 与 TDD

每项非平凡变更在 `openspec/changes/<change-id>/` 维护一份简洁规格和现有结果记录；首次实际变更时再创建目录。必要设计和证据用链接关联，普通纠错更新原记录。最少写清：完整可观察结果、需求/验收标识、范围与不做事项、允许修改路径、关键边界、适用检查和未决问题。

**按复杂度选择规格与 UI Demo：** 简单、范围闭合的修复可不另建spec，在适用原记录中留下复现、修正及验证即可；跨模块、重要契约／权限／持久化或其他复杂改动须维护简洁spec。涉及较明显的前端布局、导航或交互流程变化时，先提供可查看的UI Demo供用户审核，记录明确审核结果后再实施正式UI变更。很简单的文字修改、按钮调整等可不另出Demo，仍完成相称验证。spec和Demo是否需要按实际影响判断，不把所有修复一律升级为文档／审批套件，也不以“修复”名义绕过复杂变更的必要规格或UI审核。

工作顺序：明确目标与验收 → 维护规格并实施适用 TDD → 最小可运行切片与真实路径反馈 → 同一责任方持续修正和受影响检查 → 完整候选集中复核与验证 → 适用验收及获授权 Git 交付。

**spec 与 UI 的四原则前置检查：** 提交确认前，沿普通用户的实际目标走一遍正常、失败与恢复路径，记录：Host／Agent 各自负责什么；采用的 SDK 实际版本／原语、已存在能力和新增适配的缺口证据；用户完成目标必须做的操作、相对已有路径新增的记忆／配置／确认动作，以及可删除／合并／默认完成的步骤。区分正常提问／发送、用户自愿管理、必要权限确认和技术异常处置；新增必做的人工作业须给出不能由 Agent／SDK 完成的理由。提供可体验的最简正常路径，管理／追溯／高级范围按需展开，不能让可选管理成为实际默认必经流程。审查必须包含 spec 条款、UI 动作／可点击原型或不适用理由与反例；设计阶段与产品运行的验证结论分别记录。

**界面与交互的开工确认：** 新增或实质调整用户界面／关键交互时，先提交对应spec与可点击UI Demo，写明关键路径、状态和现有实现差异，由用户确认后再实施受影响的产品代码。Demo可用虚构资料与内存状态，明确其演示边界；实现后的截图、测试或独立复核不能替代用户的前置UI确认。现状盘点、纯后端变更或无界面影响的普通纠错，在spec说明不适用原因即可，不补造Demo。已确认且未变化的事项沿用原决定；出现实质变化时只补受影响部分。确认记录保留具体版本／摘要与用户决定；用户明确选择暂不对齐的差异另列保留，不改写为已一致。

- **确定性行为**：实现前有能检出目标行为错误的测试；修复前保留失败测试或因果复现，再做最小 GREEN 修复和必要重构，留下永久回归。保留关键正向、反向、边界、失败和禁止副作用断言。
- **探索与模型质量**：先明确实际任务、预期和观察条件，保留真实试验与失败；不伪造确定性 RED。单次成功只证明该场景及其输入、模型、工具和配置条件。
- **纯重构**：保留修改前后 GREEN 与相关等价证据。
- **文档和规范变更**：做相称的一致性、引用和范围复核，不制造产品 RED 或无意义的占位测试。

测试从需求和验收导出，不照着实现重述。环境、导入、定位器或 fixture 失败不算产品 RED；后补测试不能伪造历史失败。测试修改或删除应解释覆盖如何保留，不能通过削弱断言把失败改成成功。

从首个可运行切片起，尽早走用户正常入口、实际配置、代表输入、真实工具及适用的保存/重开、失败、取消和恢复路径。需要模型、数据或外部副作用的检查，沿用有效任务授权；缺少授权时明确未验证范围。Mock、结构校验或 SDK 导入通过不能证明真实分析成功。

真实模型评估不能仅凭模型名称相同认定配置等价。冻结并用实际SDK核对Provider/协议/线路、reasoning、thinking level、contextWindow、maxTokens、compat及相关输入限制；中继或自定义Provider可能触发通用模型默认值，必须先核对实际注册模型和请求参数。隔离测试的内存凭据替身仅替换获准配置的密钥，保留原配置校验、版本与公共生命周期；只用于评估，不作为Extension或生产接线范式。实际原配置、诊断替身、合成Provider和供应商结算费用分别报告，不能混用成绩或将SDK费用估计0写成免费。

同一责任方持续完成诊断、修复和回归。普通修正复用有效规格与授权，不为每次编辑重建文档套件、全量回归或独立审批；新增产品行为、重要契约/持久化结构、数据权限或外部影响边界，先补齐必要决定再实施受影响部分。

### 任务目标执行清单与范围管理

准备 spec 和适用的 UI Demo 时，一并编写简易的任务目标执行清单，随同提交用户确认。清单顶部写明本轮任务目标和预期交付结果，下面按实际执行阶段拆分任务，为每项写明可核对的完成条件或对应的验收条目。清单可放在 spec 或现有任务记录中。按本节可简化规格的任务，开工前直接在现有任务记录中列出目标和清单，沿用已有确认安排。

开工后，对照 spec、适用的 UI Demo 和清单推进。每项达到完成条件后立即标记完成，并简记验证结果或链接证据。受阻项保留为未完成，记录原因并继续可推进的项。用户确认调整范围后，同步更新受影响的规格、适用的 UI Demo 和清单。

1. **以原任务目标和验收为准。** 开工时明确本轮交付与验收条件。开发、排查和修复中每发现一个新问题，都对照原任务判断它影响哪项验收或受影响的使用路径。排查另一问题时发现的新问题，也按原任务重新判断。
2. **修复本次引入的回归和直接阻塞。** 在现有授权内，做恢复受影响路径或解除阻塞所需的最小修复，验证后回到清单继续执行。若修复需要扩大权限、改变公共契约或新增独立功能，先推进可做的部分，并把具体阻塞和处理选项交用户决定。等待决定期间，继续完成已获授权且不依赖该决定的事项。
3. **记录范围外问题并继续原任务。** 在现有任务记录中简要记下问题、复现线索及已知影响，留待后续处理。是否纳入本轮取决于对原任务的实际影响。同文件、改动小或方便顺手处理，都不足以作为纳入依据。发现可能造成数据损坏或越权的风险时，先暂停受影响的操作、保留现场，并继续安全可做的部分。
4. **按原验收核对完成情况。** 收尾自检和独立复核逐项核对原任务验收与清单状态，并确认每项额外改动均对应具体回归、直接阻塞或用户已批准的范围变更。以原任务及已批准变更的验收结果判断是否完成。

### Pi SDK 升级流程

用户指定目标后，由 Codex 维护统一 SDK 接入，Qoder 配合其 Extension 适配；已明确的版本与授权沿用，不重复索取相同确认。升级按以下顺序实施：

1. **固定目标和基线。** 记录用户指定的精确官方版本、升级前依赖／锁文件／实际解析版本、官方发布说明与变更来源；核对运行环境、内部接口清单、依赖覆盖、各 owner/profile 及现有 Extension。界面无实质变化时注明 UI Demo 不适用，避免无关人工步骤。
2. **隔离候选并适配。** 保全项目、原生历史／fork 指针、配置、文件和已有 FAIL／UNKNOWN；在隔离工程环境先更新官方依赖及锁文件，不共用或改写正在服务的依赖安装目录，不改官方包实现。对 OptraSentiScope 适配先保留兼容性失败，再按适用 SDD/TDD 修正；公开接口优先，内部接口及第三方覆盖逐项重核，不能删除保护或跳过断言换取通过。升级候选安装与正式运行采用分开，不自动更新其他设备或正在运行的服务。
3. **验证受影响能力。** SDK 为共享底座，执行完整适用检查、真实 SDK 的隔离集成路径及非作者独立复核；按下表在规格中固定关键项、通过标准和证据，逐项记录 PASS／FAIL／NOT_RUN／UNKNOWN，不把测试文件存在或旧版本 PASS 当成新版本证据。

| 能力 | 升级回归至少核对 |
| --- | --- |
| 来源与依赖 | 用户目标、官方发布／锁文件完整性、实际解析及 SDK 导出版本一致；无包改写；官方 Pi 传递依赖、Node 要求和第三方 overrides 兼容 |
| 会话与历史 | 新建、恢复、重启、空会话首次追加、原生版本／header／fork／branch、保存重开；原项目及会话文件／指针保全、owner／配置隔离 |
| 工具与取消 | 原生及自定义工具、嵌套调用、codemode、错误回执、停止／关闭／drain、迟到事件和已有权限／原件保护；不代 Agent 选分析步骤 |
| MCP | 官方配置加载、连接、工具发现／调用、错误与取消；普通可用范围及受管／封闭 profile 原有拒绝边界分开核对 |
| 模型接入 | 已配置 Provider／协议／线路、模型注册与流式事件、工具协议、thinking／reasoning／上下文和输入限制；配置保存、切换及恢复 |
| 上下文管理 | 系统／业务上下文、资源加载、压缩、分支恢复、嵌套执行上下文及当前运行资格；不串任务或退回未经核定的旧上下文 |
| 联网与传输 | 现有联网能力、HTTP／fetch、依赖覆盖、TLS、超时、取消、网络错误与脱敏；联网型工具和模型原生搜索分别验证 |
| 现有 Extension | 按实际影响覆盖已接入的 skill、连接器和业务插件及第三合成消费者，保留当前 Interface／owner／profile 合同和历史成果 |

工程验证默认使用隔离合成 Provider／MCP、合成资料及获准的兼容历史副本；真实模型、业务材料与凭据访问继续核对相应授权，不因升级自动启动。关键能力若缺授权而未验证，也必须保留未验证状态，不能以模拟成功代替。既有已接受的能力限制单列保留，不自动标成新版本已支持。

4. **交付及采用。** 交付说明列升级前后版本、来源及实际版本证据、OptraSentiScope 适配／内部接口与依赖覆盖变化、测试与独立复核、数据／历史兼容、未解决风险和回退方式。关键验证未通过或仍待验证时，升级不能标记完成，也不能直接投入使用。Git／CI、安装／服务采用、其他设备更新与用户产品验收按既有范围分别执行和记录。回退需使用用户指定或已明确批准的目标及触发条件，不自行降级；保留升级后新增数据，不用旧快照覆盖新成果，无法兼容时维持隔离并提交用户决策。已有明确回退授权不重复确认。

### Semantica 升级验证与回退

Semantica 升级沿用上节[Pi SDK 升级流程](#pi-sdk-升级流程)的用户目标、固定基线、隔离候选、自有适配、SDD/TDD、独立复核及交付门槛；按其实际能力执行下表，不照搬 Pi 专属会话实现。本节补充语义引擎、既有资产及环境回退的验证要求。

在新的明确私有环境准备候选，不覆盖在用解释器／依赖、不替换普通分析 Python 或系统 Python。先保全原代码、锁文件、解释器／组件身份、图与资产版本、绑定和已有结果，再核目标官方发布说明、Python／平台与原生依赖要求；安装、迁移和图重建只在获准副本执行。

| 范围 | 升级至少验证 |
| --- | --- |
| 组件与环境 | 官方来源、wheel／锁完整性、实际版本与导入路径、依赖闭包兼容、关键导入及依赖一致性；公开接口差异和内部接口例外分别记录 |
| 已有资产 | 已有本体／词汇／规则、图快照、来源清单、引用／摘要、业务方法发布版、资料修订、输入及项目绑定可准确读取和引用；旧版本、UUID、hash与原件保留，不静默切 latest、补事实或覆盖原快照。确需迁移时保留副本验证和新旧版本对应关系 |
| 语义保真与刷新 | 关系方向、时间与条件、平行／相反声明、冲突／未知、来源和必要 metadata；保存重开、新代重建、显式刷新和旧准确引用。图仍是可重建派生物，不能用图约束通过代替业务正确或来源完整 |
| 接入与失败 | 实际 Host→统一 Agent Runtime→Semantica 查询、结果交付、owner／profile、当前来源准入和撤回、分页、取消／关闭／重启、停用与原分析路径；缺失／损坏／错版不假报 ready，不静默回退成功，不扩大工具和写入权限 |
| 回退组合 | 同时固定旧代码、解释器／依赖、配置与兼容资产／图版本；在隔离副本核旧组合对升级后新增记录的兼容性，以及停图后原路径的适用边界。选择旧图仍须核当前来源资格，不能因回退复活失权资料 |

工程验证默认用真实 Semantica 的隔离合成路径及获准的历史副本；不因组件升级自动读取真实业务／凭据或调用真实模型。保留 FAIL／UNKNOWN／NOT_RUN／NOT_PROVED，不用安装成功、HTTP200或图验证通过冒充资产兼容、专业质量或用户产品验收。

交付应列明升级前后版本与来源证据、适配和依赖变化、上述资产回归、独立复核、未解决风险，以及回退目标、触发条件、执行顺序和数据保全办法。回退沿用户指定或已明确批准的安排，不自行降级；正常停止并确认清理后才切换兼容组合，保留升级后新增资产、项目、会话和报告，不用旧数据副本覆盖新成果。格式不兼容或关键验证失败／未知时维持候选隔离，说明影响交用户决策，不标升级完成或直接投入使用。Git／CI、安装、服务采用、设备更新与产品验收仍按各自授权及实际回执记录。

## 4. 独立复核与工程完成

日常自检、Codex/Qoder 接口互查和作者测试不能替代最终独立复核。复核者不得是该候选任一部分的作者；两位作者互相看代码，不自动构成完整候选的独立复核。

完整结果收尾时固定候选、规格、输入与证据，覆盖 staged、unstaged 和新增文件。提供候选提交或文件清单与摘要、验收依据、允许检查、现有结果、失败和缺口；复核上下文独立，先从验收导出关键预期，再检查实现和作者测试。

复核保持源文件、测试、规格和固定证据只读；获准检查需要的临时文件、缓存或报告只能写入明确的隔离位置。复核者独立检查关键路径与失败路径，记录检查范围、命令/结果、发现与结论；作者修复后重验受影响范围。候选变化导致的旧 PASS 失效应明确记录，不能沿用不适用的复核或 CI。

工程完成至少具备：

1. 当前规格与已确认验收一致，实际修改在授权范围内。
2. 适用目标测试、回归与质量检查完成，真实集成路径和结果有证据。
3. 独立复核完成，发现已处理；必要的用户风险接受单独记录，不写成复核 PASS。
4. 必要 CI 对应实际交付候选；变更到位后更新规格及结果记录，并完成适用 OpenSpec 归档。局部检查不代表完整交付。
5. 交付说明给出版本、验证、失败/未验证项、风险与后续点；涉及更新时说明回退方式及其数据影响。
6. 下述职责边界及复用专项最终检查已通过，或已有负责人批准且仍有效的限范围例外；批准例外不记为检查通过。

独立复核不可用时，明确未完成的复核及其影响；可继续安全、已授权的实现，但不得用作者自评代替要求的复核或宣称完整工程验收。

产品验收由用户对固定候选的适用体验和结果作出。工程检查、独立复核、CI、Git 推送、产品验收、安装与发布分别报告；任何一项不自动代替另一项。尚未运行、失败、跳过及未知结果如实保留。

### Host 与 Agent 职责边界及复用检查

开发流程的最终验收须包含本项检查，与本节要求的最终独立复核一并完成。合并或发布前，基于本次变更的实际代码、调用链及必要运行记录，按第2节通用原则确认：

- Host 承担环境、目标与业务上下文交付、权限、资源控制、交互、状态与日志展示、成果持久化和决策学习环境等职责；Agent 在授权范围内自主选择方法、工具、执行顺序及纠错方式。Host 不通过硬编码分析流程、固定步骤、方法配额或无必要的确认门槛干涉 Agent 内部运行，不代作业务判断、补计算或编排推理。
- 会话循环、工具调用、上下文管理、压缩、恢复与重试等能力优先复用既有 SDK／Runtime；新增机制须有已验证的能力缺口、证据及最小适配理由，不能以包装或统一入口掩盖平行机制。
- 必要的权限、安全、预算、取消和原件保护措施属于环境治理，应核对其实际边界，不将其误判为干涉 Agent 自主执行；已确认的业务输入输出契约与普通分析内部步骤分别检查。
- 人的操作沿本次实际 spec／UI 与运行路径核对：正常使用无需额外维护／普通读取审批，新增必做动作有目的和必要性证据；已考虑当前工作快捷路径、合理默认、合并操作与渐进披露。不能只凭“已自动化”文案通过，也不能以省操作为由替人作未授权的业务取舍。

涉及 SDK、依赖或 SDK 适配的变更，专项最终检查还须核对本规范的官方包不可修改、用户版本决定、公开接口优先、内部接口例外及上述升级回归／交付要求。源码补丁、运行时改写、来源／实际版本不一致或关键未验证不得被统一入口 PASS 掩盖；既有风险的“已登记”不等于“已修复”。

验收记录须列明本次检查范围、候选身份、证据位置、发现的问题，以及“通过／不通过／待验证”结论；不能仅凭设计声明或测试全绿判定通过。检查范围以本次变更及受影响接缝为准，不据此宣称未检查的既有实现已合规。

存在职责越界、重复建设、无合理必要性的新增人工作业或关键证据缺失时，不得标记本项验收完成。应修正并复核，或提交写明范围、理由、风险和退出条件的例外供负责人批准；未通过且未经批准例外，不得进入合并或发布。批准例外须与原“不通过／待验证”结论及未解决问题分别记录，不得改写为检查通过；例外不扩大其他任务、数据、模型、Git、安装或运行采用授权。

## 5. Git 与 CI 的精简节奏

本节规则直接核对 OptraCall 远端 `main` 提交 `15f40455083c144a185bed4aef6715c7891085dd` 的[工程规范第5节](https://github.com/gadfly-hbo/OptraCall/blob/15f40455083c144a185bed4aef6715c7891085dd/docs/engineering-workflow.md#5-git-与-ci-的精简节奏)与[单任务 CI](https://github.com/gadfly-hbo/OptraCall/blob/15f40455083c144a185bed4aef6715c7891085dd/.github/workflows/check.yml)。沿用同源 Git、独立复核、提交身份和检查规则；OptraCall 的长期分支、设备及旧任务授权不迁入本项目。此次来源与适用差异记录在[继承记录](optracall-inheritance.md#gitci-规则再次核对2026-11-11)。

### Git

远端为 `https://github.com/gadfly-hbo/OptraSentiScope.git`，`main` 为集成基线。本次用户要求建立本地及远端仓库并继承规则，首次初始化提交直接建立并推送 `main`。后续功能和修复使用独立工作分支，例如 `codex/<slug>`、`qoder/<slug>`；同一分支同一时刻保持一个明确写入者。长期专属分支按实际需要和任务决定建立，不自动复制原项目分支。

日常在已有 Git 授权内按需要提交、推送工作分支；内部修正和子任务不必每次创建 PR、全量 CI、独立复核或打包。完整变更收尾时集中一个 PR、独立复核、适用检查和获授权的 squash 合并，再安全快进本地 `main`。已有 PR 更新触发的检查照常完成，不为规避 CI 隐藏更新或扩大单个变更。

提交前核对实际暂存清单、差异、身份和公开内容；只纳入本任务文件。保留 WIP 和失败现场，不重置、清理、强制切换、改写历史或覆盖他人工作。基线变化时检查兼容性，重新验证失效部分。推送/合并不自动更新运行服务或其他机器；本项目不建立双开发端同步流程。

### Skill 测评与接入

Codex 与 Qoder 开发的 Skill 均须在接入前通过独立测评。实施者完成自检并固定候选身份后，将完整候选目录放入 `skill-eval` 仓库的 `pending/`，由用户按既有流程组织测评。测评未通过时，实施者根据反馈修订候选并重新提交测评。接入以绑定候选版本且经用户明确确认通过的测评回执为准。

Codex 直接开发的 Skill 通过测评后，由 Codex 在原变更中接续完成 Host 接缝、适用工程验证、非作者独立复核及获授权交付。接缝任务书用于本规范的 Qoder → Codex 移交流程。

沿用来源中的单向工程修正安排：用户明确确认 Skill 测评通过并移交后，Codex 的工程修正及非作者复核修正不自动触发用户复测；保留原被测身份、修正内容及覆盖安排，不将未重测写成已重测。新增能力或用户另行要求按当前有效决定处理。规则不授权自动写入其他仓库、安装 Skill 或运行模型，具体动作按当前任务范围执行。

如后续界面展示测评结果，回执绑定被测版本，缺数据不补造，收益与耗时／Token 代价共同披露；具体指标、布局和交互在本项目相应 spec／UI 中确定，不照搬原产品页面或历史回执。

### CI

OptraCall 现有工作流在所有 PR、`main` push 和手动触发时执行一个 `check` job：Ubuntu／Node 25.9.0，检出实际 PR head（其他事件为实际提交），执行 `npm ci --ignore-scripts`、`npm run check`、`npm audit --audit-level=high`；checkout 与 setup-node 使用上游工作流固定提交。它没有文档路径过滤、docs-only job 或条件跳过。

本项目当前仅有文档，没有 `package.json`、锁文件、产品检查入口或 CI。用户于2026-11-11明确选择：“本轮按纯文档规则合并，CI 记录未建立；产品搭建时复用同款 CI”。本轮据下表完成相称检查和非作者复核，通过独立工作分支、单 PR 及获授权 squash 交付；不为运行上游 CI 而引入无关产品依赖，不创建空流程，也不声称上游已有文档 CI 豁免。该安排是用户对本轮的明确决定，不是新增的通用跳过规则。

通用产品搭建时复用上游同款 CI，结合届时已确认技术栈建立实际检查入口，并重新核对源工作流及适用依赖／版本授权。PR 核对实际 head，合并后核对 main push；没有空流程或重复矩阵。无真实凭据、模型或业务数据进入 CI。本地检查不表述为 CI PASS，平台专有验收、真实模型与产品验收分别记录，交付核对实际检查与提交身份。

| 修改范围 | 验证选择 |
| --- | --- |
| 纯非运行时文档 | 差异、内容一致性、引用、范围和适用独立复核；不安装无关产品依赖 |
| 已知消费者且影响闭合 | 使用有证据的影响映射运行对应检查，并报告遗漏范围 |
| 运行时、安全/权限、持久化、公共接口、共享依赖、构建/CI 自身或影响不明 | 运行届时定义的完整适用检查及受影响真实路径；平台专有验收另行报告 |

混合变更只有全部对象被可靠覆盖时才能采用定向检查；否则采用完整适用检查。检查选择逻辑不能批准自己降级。每次报告实际选择、结果和未跑项，局部 PASS 不表述为全量通过。保留失败日志，先解释原因再重试；无解释的绿色重跑不关闭原始失败。

## 6. Extension 接入与版本交付

Extension 实施者提供可独立理解的交付说明，涵盖解决的任务、输入输出、版本和依赖、权限与数据出口、适用测试、已知限制、接入与停用方式。分析资产、连接器和业务插件按任务和 SDK 能力选择技术映射。

Codex 核对接入兼容性、统一 Runtime 的真实调用路径以及受影响的主链路回归。验证应能发现插件自行创建 Runtime、绕过权限或破坏宿主任务/会话管理等问题；公共边界与必要契约测试随实际接入建立。本次不创建插件协议或调度平台。

后续试用或部署交付应给出源码提交、构建／实际运行版本、模型及关键配置、入口、体验步骤与已知缺口。设备准备、依赖安装、服务更新、远程访问和报告移动按有效授权执行，代码与持久业务数据分离，保留本地变化及新增成果。反馈关联实际版本、复现步骤、预期与实际以及可安全提供的证据；体验反馈不自动等于正式产品验收。

## 7. 数据、资源与副作用

Host 的权限与执行环境控制真实资源及副作用，不能仅靠提示词。授权范围内的普通分析迭代无需逐步确认；范围扩大、敏感内容外传、覆盖原件或真实业务动作，依据有效授权处理。开发与 Git 权限不自动授予业务数据、模型调用、安装、发布或生产切换权限。

本仓库公开。凭据、客户数据、私有经营资料、原始会话和运行日志保留在授权本地位置；公开样例使用合成或明确获准公开的材料。审查模型请求、工具结果、日志和报告的实际数据出口，不能从“本地计算”推导“零数据外传”。`.gitignore` 不替代内容审查。

Agent 建议、用户采纳、实际执行和效果验证分别记录。取消、超时或恢复中不明的副作用保留 UNKNOWN，不假定成功，也不盲目重放。代码回退不保证数据回退；数据兼容性和未知影响需另行核对。

## 8. 证据与进度

源码、长期测试、规格、正式决定和验收结论进入仓库的适用位置；原始命令输出、日志、候选清单和诊断现场保留在该任务明确的本地持久证据位置，初始本地检查可使用被忽略的 `.local/`。禁止把应保留的唯一证据放在临时目录。

记录候选和输入身份、实际命令与退出结果、适用环境/配置、复核范围及失败/未知。重要结论能追溯到验收与可访问证据；不只交摘要或哈希。进度说明验收推进、实际结果、缺口和下一步，普通里程碑不构成新的审批点。用户明确停止时停止相应任务，保留现场与返回点。
